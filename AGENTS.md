- Booking is public (guest checkout): booking server fns are keyed by the unguessable intent id, and post-booking guest actions go through `appointments.manage_token` verified server-side in `appointment-actions.server.ts` — why: patients book without an account but must only reach their own booking.
- SEO landing pages live in `seo_pages` (service-role only, admin-checked server fns in `src/lib/seo-pages.functions.ts`) and render at top-level `/$slug`; new top-level routes must be added to `RESERVED_SLUGS` in `src/lib/seo-pages.ts` — why: a page slug would otherwise shadow or collide with a real route.
- Condition-page head metadata comes from the browser-safe shared SEO head helper using loaded page identity; optional therapist listing headings travel through the same CSV/editor/public pipeline — why: newly imported pages need no bespoke metadata or wording changes.
- Matching enquiries are validated server-side, stored service-role-only with explicit consent evidence and atomically rate-limited before one fixed-recipient email — why: sensitive guest submissions must survive email failures without public read access.
- SEO pages move Draft → Clinical review → Approved → Published via `seo_pages.status`; a DB trigger derives `published` and blocks approve/publish without reviewer name, qualifications and date — why: nothing goes live without clinical sign-off.
- Therapist Therapy approach reuses the profile title field; SEO recommendations are a separate editor-provided list included in CSV and clinical review, while expertise matching stays unchanged — why: therapy methods must not be conflated with conditions or fabricated from therapist titles.
- Post-session review reminders use per-appointment Inngest sleepUntil workflows, signed server callbacks and managed email idempotency; never add email queues or polling jobs — why: timing is durable while cancellation and existing reviews are checked at send time.
- Admin visibility changes update only `therapist_profiles.published` for approved, non-rejected profiles; rejection clears approval, and admin mutations explicitly attach the current session bearer — why: hiding must preserve therapist access while rejection revokes approval and every action remains authenticated and admin-checked.
- Public directory text matching lives in a browser-safe therapist-search helper and matches name or individual expertise areas before applying existing filters — why: search stays testable without changing filter semantics.
- App notification recipient preferences are shared by admin recipient resolution and both email send paths — why: direct booking or calendar notifications must respect the same exclusions without changing account access.
- Condition-page therapist cards come from the browser-safe `pickSeoTherapists` helper: only exact expertise matches sit under the speciality heading, and any top-up is a separately labelled broader-support list — why: pages must never imply a therapist specialises in a condition they didn't select.
- Partner enquiries (/partners) follow the matching-enquiry pattern: shared browser-safe schema in `partner-enquiry.ts`, service-role-only `partner_enquiries` table with atomic rate-limited RPC, one fixed-recipient email, and admin-checked list/update fns for `/admin/partners`; campaign source (UTM/ref/referrer) is captured client-side per tab — why: B2B leads must survive email failures and stay attributable to outreach campaigns without public read access.
- Stripe environment is decided server-side only via `src/lib/payments-environment.ts` (production build or production host = live; sandbox only in preview); clients never send it and the webhook rejects sandbox events in production — why: a client-chosen environment let production bookings be "paid" with test cards.
- Notification exclusions and the preview admin inbox are server settings (`NOTIFICATION_EXCLUDED_EMAILS`, comma-separated; `PREVIEW_ADMIN_EMAIL`), never hard-coded personal addresses — why: keeps personal emails out of the code repository.
- When a booking's money and appointment fall out of step (paid but not confirmed in Cal.com, or a cancellation refund fails), call `notifyBookingNeedsReview` in `booking.server.ts` to email admins; required Cal.com booking questions are auto-answered by browser-safe `calcom-booking-fields.ts` (never phone numbers), and failed webhook events are forgotten so Stripe retries them — why: six paid checkouts once sat unbooked for weeks with nobody notified.
